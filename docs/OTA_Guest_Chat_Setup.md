# แชทกับลูกค้า OTA ผ่านอีเมล (Email-as-Chat Bridge)

คุยกับลูกค้าที่จองผ่าน Agoda / Booking.com ได้จาก **หน้าแชทในระบบ (Admin → Chat → Omni-Channel Inbox)**
โดยไม่ต้องขอ API จาก OTA — ใช้กลไก "อีเมลแฝง (masked alias)" ที่ OTA ให้มากับทุกการจองอยู่แล้ว

## หลักการทำงาน

```
ลูกค้าพิมพ์ในแอป OTA ──▶ OTA ส่งอีเมลจาก relay (เช่น xxx@agoda-messaging.com) ──▶ กล่องเมลที่พัก
                                                                                      │ ระบบดึง (IMAP ทุก 3 นาที)
                                                                                      ▼
ลูกค้าเห็นในแอป OTA ◀── OTA relay ต่อ ◀── ระบบส่งอีเมลตอบ (SMTP) ◀── พนักงานพิมพ์ตอบในหน้าแชท
```

- **ขาเข้า**: อีเมลที่มาจากโดเมน relay ของ OTA จะถูกดึงเข้าเป็นข้อความแชทอัตโนมัติ
  (แยกบทสนทนาต่อลูกค้า ตาม alias) พร้อมจับคู่เลขการจองในระบบ (Reservation.OTA_Booking_ID)
  ถ้าเจอเลข Booking Id ในอีเมล — แสดงเป็น tag "จอง #xxxx" ในบทสนทนา
- **ขาออก**: พนักงานพิมพ์ในหน้าแชทตามปกติ ระบบส่งเป็นอีเมลตอบกลับไปที่ alias เดิม
  แบบต่อ thread (Re: หัวเรื่องเดิม + In-Reply-To) → OTA จับคู่กลับไปที่การจองถูกใบ
  ลูกค้าเห็นเป็นข้อความแชทในแอปของเขาเอง
- **รูป/ไฟล์แนบ** (รูปภาพ + PDF ≤ 10MB): ขาเข้าถูกเก็บที่ `~/Images/ChatFiles/{conversationId}/`
  และแสดงในแชท
- **แจ้งเตือน**: มีข้อความใหม่ → แจ้ง Telegram กลุ่มพนักงานทันที พร้อมลิงก์เปิดหน้าแชท

## การตั้งค่า (ทำครั้งเดียว)

1. **เปิดช่องทาง**: Admin → Chat → ตั้งค่าช่องทาง (ChannelSettings) → เปิดสวิตช์ **Email**
   และตั้งค่าในการ์ด Email:
   | ค่า | ค่าเริ่มต้น | ความหมาย |
   |---|---|---|
   | `fromDomains` | `agoda-messaging.com, mchat.booking.com, guest.booking.com` | โดเมนที่ถือว่าเป็น "ข้อความลูกค้า" (คั่นจุลภาค เพิ่มได้) |
   | `pollMinutes` | 3 | รอบดึงอีเมล (นาที) |
   | `processedLabel` | `Chat-Processed` | โฟลเดอร์/label ที่ย้ายอีเมลที่ประมวลผลแล้ว |
   | `notifyTelegram` | 1 | แจ้ง Telegram เมื่อมีข้อความใหม่ |
   | `signature` | (ว่าง) | ลายเซ็นต่อท้ายอีเมลตอบกลับ เช่น ชื่อที่พัก + เบอร์โทร |
2. **กล่องเมลขาเข้า (IMAP)**: ใช้ค่าเดียวกับระบบอ่านอีเมลจอง STAAH
   (Admin → Settings → Accounting Integration → ส่วนอ่านอีเมลจอง: `Email_Rsv_ImapServer/Username/Password`)
   — ต้องเป็นกล่องเมลเดียวกับที่ OTA ส่งข้อความลูกค้ามาหา
3. **ขาออก (SMTP)**: ใช้ค่ากลางของระบบ (ศูนย์รวมการตั้งค่าระบบ: `SMTP`, `SMTP_Port`,
   `SMTP_EnableSsl`, `Email_From`, `Email_Password_From`)
   ⚠️ `Email_From` ต้องเป็น **อีเมลเดียวกับที่ลงทะเบียนไว้กับ OTA** — ไม่งั้น relay ของ OTA
   จะไม่รู้ว่าเป็นที่พักไหนและอาจไม่ส่งต่อ
4. ไม่ต้องรัน migration เพิ่ม (ใช้ตาราง OmniChannel เดิมจาก PHASE15)
   — แต่ต้อง **build + deploy DLL ใหม่** (มีไฟล์ใหม่ `Class/Services/EmailChatService.cs`)

## OTA ไหนใช้ได้บ้าง (ข้อเท็จจริง ณ ส.ค. 2026)

| OTA | ใช้ได้? | หมายเหตุ |
|---|---|---|
| **Agoda** | ✅ | ทุกการจองมี alias `xxx@agoda-messaging.com` — ตอบอีเมลแล้ว relay เข้าแชทในแอปลูกค้า |
| **Booking.com** | ✅ | alias `xxx@guest.booking.com` / ข้อความจาก `mchat.booking.com` — ตอบกลับ relay ได้ (อีเมลแจ้งเตือนบางประเภทเป็น no-reply จะตอบไม่ได้ ระบบจะ log ว่าส่งไม่สำเร็จ) |
| Airbnb | ✅ (เพิ่มโดเมนเอง) | เพิ่ม `reply.airbnb.com` ใน fromDomains |
| Trip.com / Expedia | ⚠️ บางกรณี | ไม่ให้ alias ทุกการจอง — ถ้าอีเมลไหนมี reply-to ตอบได้ก็ใช้ได้ ต้องเพิ่มโดเมนเอง |
| Walk-in / จองตรง | ✅ | อีเมลจริงของลูกค้า — เพิ่มการคุยได้ผ่านช่องทางอื่น (LINE ฯลฯ) อยู่แล้ว |

## ข้อจำกัดที่ควรรู้

- **ลูกค้าต้องทักมาก่อน** (หรือมีอีเมลจาก OTA ที่มี alias อย่างน้อย 1 ฉบับ) —
  ระบบถึงจะรู้ alias สำหรับตอบกลับ; เริ่มคุยก่อนฝ่ายเดียวไม่ได้ถ้ายังไม่เคยมีอีเมล
- **ดีเลย์**: ขาเข้าช้าสุด = รอบ poll (ค่าเริ่มต้น 3 นาที) + เวลาที่ OTA relay (ปกติไม่กี่วินาที–นาที)
  ไม่ใช่ real-time แบบ websocket แต่เพียงพอกับการคุยเรื่องการจอง
- alias ของ OTA **หมดอายุหลังเช็คเอาท์ระยะหนึ่ง** (Agoda ~ไม่กี่สัปดาห์) — คุยย้อนหลังนาน ๆ ไม่ได้
- อีเมลตอบกลับเป็น **ข้อความล้วน** (plain text) — ตั้งใจ เพื่อให้ relay ของ OTA แสดงผลชัวร์ที่สุด
- ระบบค้นเฉพาะอีเมล "ยังไม่อ่าน" จากโดเมนที่ตั้งไว้ — **ไม่แตะอีเมลจอง STAAH**
  (ระบบ intake ค้นแยกด้วยเงื่อนไข from ของตัวเอง ทำงานคู่กันในกล่องเดียวได้)

## การติดตาม / แก้ปัญหา

- Log ทุกเหตุการณ์อยู่ใน Logs หมวด **EmailChat** (รับข้อความ / ส่งไม่สำเร็จ / IMAP error)
- ข้อความขาออกที่ส่งอีเมลไม่สำเร็จ → DeliveryStatus = `FAILED` (ดูใน DB `OmniChannel_Messages`)
  สาเหตุที่พบบ่อย: SMTP ยังไม่ตั้งค่า, alias หมดอายุ, อีเมลต้นทางเป็น no-reply
- อีเมลลูกค้าที่ประมวลผลแล้วถูกย้ายไปโฟลเดอร์ `Chat-Processed` ในกล่องเมล (ตรวจย้อนหลังได้)
