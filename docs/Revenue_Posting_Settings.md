# การลงบันทึกรายได้ — สวิตช์เปิด/ปิด 3 ตัว

ตั้งค่าที่ **Admin → Settings → Accounting Integration** (ทั้ง 3 ตัว **ค่าเริ่มต้น = ปิด**
เพื่อไม่ให้พฤติกรรมเดิมเปลี่ยนเองหลัง deploy — เปิดเมื่อผู้ทำบัญชีพร้อม)

จากการไล่โค้ดเส้นทางเงินทั้งระบบ พบรายได้ 3 ทางที่ **เกิดขึ้นจริงแต่ไม่เคยเข้าบัญชี**
แต่ละทางมีสวิตช์ของตัวเอง เปิดเฉพาะที่ต้องการได้

| สวิตช์ | ปิดอยู่ = เกิดอะไร | เปิดแล้ว = ระบบทำอะไร |
|---|---|---|
| **ขายหน้าร้านไม่ออกใบกำกับ → รวบรายวัน**<br />`Nexaacc_PosDailyRollup` | ขายที่ไม่ติ๊ก "ออกใบกำกับภาษีในระบบ" ไม่ขึ้น NextAcc เลย | รวบเป็น **ใบรับเงินสด 1 ใบ/วัน/แหล่งรับเงิน** (Dr เงินสด · Cr รายได้สินค้า · Cr ภาษีขาย) + ตัดต้นทุน (Dr COGS · Cr สินค้าคงเหลือ) |
| **รูมเซอร์วิส → ลงบัญชี**<br />`Nexaacc_RoomServiceRevenue` | ออเดอร์ที่ลูกค้าจ่ายเอง (โอน/เงินสด) ไม่ถูกบันทึกที่ไหนเลย และ**ทุก**ออเดอร์ไม่เคยตัดต้นทุน/สต๊อก | จ่ายเอง → **ใบรับเงินสด 1 ใบ/วัน/วิธีจ่าย** + COGS · ลงบิลห้อง → **COGS อย่างเดียว** (รายได้ไปกับใบเสร็จเช็คเอาท์อยู่แล้ว ไม่โพสต์ซ้ำ) |
| **รายได้ค่าห้องจาก OTA**<br />`Nexaacc_OtaRoomRevenue` | การจองจากอีเมล OTA ถูกสร้างแบบ "ไม่ออกใบเสร็จ" → **รายได้ค่าห้องไม่เข้าบัญชีเลย** | ต่อการจอง หลังเลยวันเช็คเอาท์: **Dr ลูกหนี้ OTA · Cr รายได้ห้อง · Cr ภาษีขาย** (ยอดเต็มที่ลูกค้าจ่าย OTA) |

## รายละเอียดแต่ละตัว

### 1) ขายหน้าร้านรวบรายวัน (มีมาก่อน)
ทำงานกับแถว `Product_Out` ที่ `Remark='ขาย'` และไม่มีเลขใบเสร็จ · marker `Pos_Rollup_Ref`
· เอกสารสรุปชื่อ `POSDAY-{yyyyMMdd}-{แหล่งรับเงิน}` · การขายที่ **ติ๊กออกใบกำกับ** ยังยิงทีละใบเหมือนเดิม

### 2) รูมเซอร์วิส (ใหม่)
- ทำงานกับ `Guest_Room_Service_Orders` ที่ `Order_Status` ไม่ใช่ CANCELLED/PENDING ของ **วันที่ผ่านไปแล้ว**
- แยกตาม `Payment_Method`:
  - `CASH` / `TRANSFER` (ลูกค้าจ่ายเอง) → ใบรับเงินสดสรุป `RSDAY-{yyyyMMdd}-{วิธีจ่าย}` + COGS
  - `CHARGE_TO_ROOM` (ลงบิลห้อง) → **COGS อย่างเดียว** — ยอดนี้ถูกรวมในบิลเช็คเอาท์อยู่แล้ว
    (`Checkout.aspx.cs` บวก `CHARGE_TO_ROOM` เข้ายอดรวม) จึงไม่โพสต์รายได้ซ้ำ
- ต้นทุนใช้ `Product.Cost_Price` ต่อสินค้า · marker `Guest_Room_Service_Orders.Acct_Post_Ref`

#### ค่าบริการรูมเซอร์วิส (Service Charge)
ตั้งที่ **Admin → Room Service → ตั้งค่าเปิด-ปิดสั่งของ** (คนละหน้ากับสวิตช์บัญชี) — เลือกได้ 3 แบบ:

| โหมด | ความหมาย | ตัวอย่าง |
|---|---|---|
| `PERCENT` | % ของยอดสินค้า | ตั้ง 10 → สั่ง ฿500 บวก ฿50 |
| `PER_ITEM` | บาท **ต่อชิ้น** | ตั้ง 5 → สั่ง 3 ชิ้น บวก ฿15 |
| `PER_ORDER` | บาท **ต่อครั้ง** | ตั้ง 20 → บวก ฿20 ไม่ว่าสั่งกี่ชิ้น |
| `NONE` | ไม่คิด (ค่าเริ่มต้น) | — |

ตั้ง **เพดานสูงสุด** ได้ (0 = ไม่จำกัด) และตั้ง **ชื่อที่แสดงให้ลูกค้า** ได้ (ค่าเริ่มต้น "ค่าบริการ")

- ลูกค้าเห็นแยกบรรทัดในตะกร้า (ค่าสินค้า / ค่าบริการ / รวม) — คำนวณสดขณะเลือกสินค้า
- **ยอดสั่งขั้นต่ำนับเฉพาะค่าสินค้า** ไม่รวมค่าบริการ
- ยอดที่บันทึกจริง **คำนวณใหม่ฝั่งเซิร์ฟเวอร์เสมอ** ตอนกดสั่ง (ไม่เชื่อยอดจากหน้าเว็บ)
- เก็บเป็น snapshot ในออเดอร์ (`Service_Charge`) → แก้การตั้งค่าทีหลังไม่กระทบบิลเก่า
- `Total_Amount` ของออเดอร์รวมค่าบริการแล้ว ⟹ **ยอดลงบิลห้องตอนเช็คเอาท์รวมค่าบริการอัตโนมัติ**
- ฝั่งบัญชี: ใบรับเงินสดสรุปรายวันจะมี **2 บรรทัด** (ค่าสินค้า + ค่าบริการ) ·
  แยกบัญชีรายได้ค่าบริการได้โดย map `SERVICE_CHARGE_REVENUE` ในผังบัญชี (ไม่ตั้ง = ใช้บัญชีรายได้เดิม)
- ต้องรัน migration `PHASE18_21`

### ตั้งค่ารายสินค้า — รวมใบสรุปรายวันหรือไม่ (PHASE18_24)
ตั้งที่ **ศูนย์ตั้งค่า → ตั้งค่าลงบัญชีรายสินค้า** — สวิตช์ต่อสินค้า `Product.Include_In_Daily_Rollup`

- **ติ๊ก (ค่าเริ่มต้น)** = รวมใบสรุปรายวันตามปกติ — เหมือนเดิมทุกประการ
- **เว้นว่าง** = การขายสินค้านั้น**ไม่ถูกลงรายได้/ต้นทุน**ทั้งใน POS rollup และใบสรุปรูมเซอร์วิส
  (แถว `Product_Out` ถูก mark `EXCLUDED-POSDAY-...` — ตรวจย้อนหลังได้ว่าข้ามเพราะตั้งค่า ไม่ใช่ตกหล่น)

ตัวอย่าง: **หมูกระทะ** ที่ตกลงกับผู้ทำบัญชีให้รายได้ไปรวมกับค่าห้อง — ชาร์จเข้าห้องไปกับใบเสร็จ
เช็คเอาท์อยู่แล้ว จึงปิดตัวนี้กันเข้าใบสรุปรายวันซ้ำอีกทาง

**ไม่กระทบ (ตั้งใจ):** ขายที่ออกใบกำกับในระบบ (ออกใบจริงรายใบเหมือนเดิม) · ชาร์จเข้าห้อง
(ไปกับใบเสร็จเช็คเอาท์) · การตัดจำนวนสต๊อก · ยังไม่รัน PHASE18_24 = รวมทุกสินค้าเหมือนเดิม

⚠️ ข้อควรรู้เชิงบัญชี: ปิดสวิตช์ = เงินสดที่รับจริงของสินค้านั้นจะ**ไม่ปรากฏในใบสรุปรายวัน**
— ใช้เมื่อรายได้ถูกลงทางอื่นแล้ว (เช่น รวมกับค่าห้อง) หรือผู้ทำบัญชีจัดการเองต่างหาก

### 3) รายได้ค่าห้องจาก OTA (ใหม่)
- เงื่อนไขที่จะถูกโพสต์: มี `OTA_Channel`, เลยวันเช็คเอาท์, ยอด > 0, สถานะไม่ใช่ยกเลิก/ไม่มาเช็คอิน,
  และ **ยังไม่มีใบเสร็จในระบบ** (ถ้ามีใบเสร็จอยู่แล้ว = รายได้เข้าไปทางนั้นแล้ว ระบบจะไม่โพสต์ซ้ำ)
- GL ตาม `docs/OTA_Settlement_Design.md` เคส A — เงินที่ OTA โอนเข้ามาจริงค่อยไปตัดลูกหนี้ก้อนนี้
  ตอนปิดงวด payout (ค่าคอม OTA เป็นค่าใช้จ่ายแยก + §83/6 ภ.พ.36)
- **ต้องตั้งก่อนใช้งาน:**
  1. map บัญชี `OTA_RECEIVABLE` (ลูกหนี้ OTA) ใน `Accounting_Account_Mapping` — migration `PHASE18_11` ใส่แถวไว้แล้ว ต้องกรอกรหัสบัญชีจริง
  2. กด **"ดึง Chart of Accounts"** ให้ได้ GUID บัญชีจาก NextAcc
  3. ตั้ง **Company ID** ให้ใช้ company endpoints ได้
  - ถ้ายังไม่ครบ ระบบ **ข้ามการโพสต์และเขียน log แจ้ง** (เตือนซ้ำทุก 6 ชม.) — ตั้งใจให้ข้าม
    ดีกว่าโพสต์เป็น "เงินสด" ผิด ๆ ทั้งที่ยังไม่ได้รับเงินจริงจาก OTA
- marker `Reservation.Ota_Revenue_Ref`

## การติดตั้ง

1. รัน `Database/PHASE18_Migration_20_Revenue_Posting.sql`
   (สำหรับ OTA ต้องมี `PHASE18_Migration_11_OTA_Settlement.sql` ด้วย)
2. Build + deploy (ไฟล์ใหม่ `Class/Integration/RevenuePostingService.cs`)
3. เปิดสวิตช์ที่ต้องการใน Accounting Integration

**ข้อมูลย้อนหลัง:** migration ทำเครื่องหมาย `LEGACY` ให้ออเดอร์รูมเซอร์วิสทั้งหมด และการจองที่เช็คเอาท์
ไปแล้วก่อนติดตั้ง → **ไม่ถูกลงบัญชีย้อนหลัง** (กันเอกสารทะลักตอนเปิดครั้งแรก)
ถ้าต้องการลงย้อนหลังบางช่วง ให้เคลียร์ marker เป็น `NULL` เฉพาะช่วงนั้นเอง เช่น

```sql
-- ตัวอย่าง: ลงย้อนหลังรูมเซอร์วิสเดือน ก.ค. 2026
UPDATE Guest_Room_Service_Orders SET Acct_Post_Ref = NULL
WHERE Acct_Post_Ref = 'LEGACY' AND Order_Date >= '2026-07-01' AND Order_Date < '2026-08-01';
```
